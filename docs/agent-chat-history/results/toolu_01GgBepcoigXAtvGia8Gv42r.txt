- `payment_attempts(id, order_id, outcome {succeeded, declined}, idempotency_key, created_at, unique(order_id, idempotency_key))`

- `home_sections(id, key unique, type, title, position, enabled, config jsonb)`, `banners(id, section_id, title, subtitle, image_url, cta_label, cta_href, position, starts_at, ends_at)`.

**Checkout invariant** (stated in `docs/architecture.md`, checked by tests):
> A key is `reserved` ⇔ its order item's order is `pending_payment` and not past `expires_at` (until swept); `sold` ⇔ order `paid`; `available` ⇔ no `order_item_id`. For every order item, the number of linked keys = `quantity`.

**Transactions** (READ COMMITTED + explicit row locks; every step is one DB transaction, so a crash or DB error rolls back completely):
1. **Create order** `POST /api/orders` — headers `Idempotency-Key` (client UUID per checkout attempt, kept in sessionStorage), body `{items:[{offerId,quantity}], expectedTotalCents}`:
   a. Sweep this user's and the requested offers' expired orders (step 4) first.
   b. `INSERT orders … ON CONFLICT (user_id, idempotency_key) DO NOTHING RETURNING id`; on conflict load the existing order: same `request_hash` → return it (200); different payload → 422. A concurrent duplicate blocks on the unique index until the first commits, then takes the conflict path ⇒ exactly one order.
   c. Lock offers `SELECT … FROM offers WHERE id = ANY($1) ORDER BY id FOR SHARE`; inactive/missing → 409 `offer_unavailable`; recomputed total ≠ expected → 409 `price_changed` with current prices.
   d. Insert order items with price/title/seller snapshots.
   e. Per item, **in ascending offer_id order** (deadlock-free): `UPDATE offer_keys SET status='reserved', order_item_id=$item WHERE id IN (SELECT id FROM offer_keys WHERE offer_id=$o AND status='available' ORDER BY id LIMIT $qty FOR UPDATE SKIP LOCKED) RETURNING id`; fewer than `qty` rows → rollback whole tx → 409 `out_of_stock` naming the offer and available count. Multi-item orders are all-or-nothing.
   f. Cancel the user's other `pending_payment` orders (releases their keys) so one user cannot hoard stock; commit. Reservation TTL 15 min.
2. **Pay** `POST /api/orders/{id}/payments` — header `Idempotency-Key`, body `{outcome: "success" | "decline"}` (demo control):
   - `SELECT … FROM orders WHERE id=$1 AND user_id=$2 FOR UPDATE` (else 404).
   - Same attempt key already recorded → return the recorded result.
   - `paid` → 200 with order (idempotent); `cancelled`/`expired` or `expires_at < now()` → expire+release in this tx, 410 `order_expired`.
   - decline → insert attempt `declined`; order stays `pending_payment`, keys stay reserved until expiry so the buyer can retry (realistic retry semantics).
   - success → insert attempt `succeeded`; `UPDATE orders SET status='paid', paid_at=now() WHERE id=$1 AND status='pending_payment'` (compare-and-set, must affect 1 row); `UPDATE offer_keys SET status='sold' WHERE order_item_id = ANY(items) AND status='reserved'` must affect exactly Σquantity rows else rollback 500; delete purchased offers from cart; commit.
3. **Cancel** `POST /api/orders/{id}/cancel`: pending → `cancelled`, keys → available (`order_item_id` NULL) in one tx.
4. **Expiry sweep** (single statement set in one tx): `UPDATE orders SET status='expired' WHERE status='pending_payment' AND expires_at<now() RETURNING id` → release their keys. Runs inline before create/pay (so stock recovers even when the free-tier instance was asleep) and on a 1-minute ticker.
5. Network interruption: client retries with the same idempotency keys and gets the committed result; UI shows "checking your order…" and re-fetches `GET /api/orders/{id}`.

**Payment UX:** `/checkout/:orderId/pay` titled "Demo payment — no real money is charged": order summary, timer to reservation expiry, buttons **Simulate successful payment** and **Simulate declined payment**; decline shows error with retry/cancel; success → `/orders/:id` with keys (copy button).

**Auth & security:**
- Passwords: bcrypt cost 12; length 8–72 bytes (bcrypt limit) enforced; email normalised; generic "invalid email or password"; unknown-email path still runs a bcrypt compare against a dummy hash (timing).
- Sessions: 32-byte random token; DB stores SHA-256; new session on every login/registration (no fixation); absolute expiry 14 days, idle expiry 2 days (`last_seen_at` updated at most every 5 min); logout deletes the row and clears the cookie.
- Cookie: prod `__Host-sid` (Secure, HttpOnly, Path=/, no Domain, SameSite=Lax); dev `sid` without Secure on http://localhost — chosen by config, never by request.
- CSRF: Go stdlib `http.CrossOriginProtection` (Go ≥1.25; local 1.27) on all non-safe methods — rejects requests whose `Sec-Fetch-Site` is cross-site or whose `Origin` doesn't match, with `AddTrustedOrigin` for the exact Vercel production origin and `http://localhost:5173`; plus SameSite=Lax and JSON-only bodies (`Content-Type: application/json` required). Day-2 deploy step **verifies** Vercel forwards `Origin`/`Sec-Fetch-Site` and records findings; if the rewrite alters them, fall back to an explicit `Origin`-against-allowlist check (`ALLOWED_ORIGINS` env).
- Proxy: Render API trusts `X-Forwarded-For` only for logging; rate limiting (login/register: 10/min per IP + 5/min per email, in-memory token bucket) documented as best-effort on a single instance.
- Authorization: every order/cart query includes `user_id = $session_user`; non-owned order → 404; UUID ids; product/cart/pending-order responses never include key material; keys AES-256-GCM encrypted with `KEY_ENCRYPTION_KEY`, decrypted only in `GET /api/orders/{id}` for the owner when `paid`.
- Headers (Vercel config): CSP (self + image origins), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `frame-ancestors 'none'`.

**REST API:** `GET /home`, `GET /home/sections/{key}` · `GET /products` (q, platform, region, type, min_price, max_price, sort, page, page_size → items, total, facets) · `GET /search/suggest` · `GET /products/{slug}` · `GET /platforms|regions|types` · `POST /auth/register|login|logout`, `GET /auth/me` · `GET /cart`, `PUT|DELETE /cart/items/{offerId}`, `POST /cart/merge` · `POST /orders`, `POST /orders/{id}/payments`, `POST /orders/{id}/cancel`, `GET /orders`, `GET /orders/{id}` · `GET /healthz`.
