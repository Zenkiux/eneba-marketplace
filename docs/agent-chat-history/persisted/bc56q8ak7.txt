see Pay)\n- `order_items(id, order_id, offer_id, product_id, seller_id, unit_price_cents, quantity check 1..10, title_snapshot, seller_snapshot)`\n- `offer_keys(id, offer_id, code_ciphertext bytea, code_fingerprint bytea unique, status key_status{available,reserved,sold}, order_item_id fk null, updated_at)` with **CHECK** `(status='available') = (order_item_id IS NULL)`; partial index `(offer_id, id) WHERE status='available'`.\n- `payment_attempts(id, order_id, outcome {succeeded, declined}, idempotency_key, created_at, unique(order_id, idempotency_key))`\n- `cart_items(user_id, offer_id, quantity 1..10, added_at, PK(user_id, offer_id))`; guest cart in localStorage, merged on login.\n- `home_sections(id, key unique, type, title, position, enabled, config jsonb)`, `banners(id, section_id, title, subtitle, image_url, cta_label, cta_href, position, starts_at, ends_at)`.\n\n**Checkout invariant** (stated in `docs/architecture.md`, checked by tests):\n> A key is `reserved` ⇔ its order item's order is `pending_payment` and not past `expires_at` (until swept); `sold` ⇔ order `paid`; `available` ⇔ no `order_item_id`. For every order item, the number of linked keys = `quantity`.\n\n**Transactions** (READ COMMITTED + explicit row locks; every step is one DB transaction, so a crash or DB error rolls back completely):\n1. **Create order** `POST /api/orders` — headers `Idempotency-Key` (client UUID per checkout attempt, kept in sessionStorage), body `{items:[{offerId,quantity}], expectedTotalCents}`:\n   a. Sweep this user's and the requested offers' expired orders (step 4) first.\n   b. `INSERT orders … ON CONFLICT (user_id, idempotency_key) DO NOTHING RETURNING id`; on conflict load the existing order: same `request_hash` → return it (200); different payload → 422. A concurrent duplicate blocks on the unique index until the first commits, then takes the conflict path ⇒ exactly one order.\n   c. Lock offers `SELECT … FROM offers WHERE id = ANY($1) ORDER BY id FOR SHARE`; inactive/missing → 409 `offer_unavailable`; recomputed total ≠ expected → 409 `price_changed` with current prices.\n   d. Insert order items with price/title/seller snapshots.\n   e. Per item, **in ascending offer_id order** (deadlock-free): `UPDATE offer_keys SET status='reserved', order_item_id=$item WHERE id IN (SELECT id FROM offer_keys WHERE offer_id=$o AND status='available' ORDER BY id LIMIT $qty FOR UPDATE SKIP LOCKED) RETURNING id`; fewer than `qty` rows → rollback whole tx → 409 `out_of_stock` naming the offer and available count. Multi-item orders are all-or-nothing.\n   f. Cancel the user's other `pending_payment` orders (releases their keys) so one user cannot hoard stock; commit. Reservation TTL 15 min.\n2. **Pay** `POST /api/orders/{id}/payments` — header `Idempotency-Key`, body `{outcome: \"success\" | \"decline\"}` (demo control):\n   - `SELECT … FROM orders WHERE id=$1 AND user_id=$2 FOR UPDATE` (else 404).\n   - Same attempt key already recorded → return the recorded result.\n   - `paid` → 200 with order (idempotent); `cancelled`/`expired` or `expires_at < now()` → expire+release in this tx, 410 `order_expired`.\n   - decline → insert attempt `declined`; order stays `pending_payment`, keys stay reserved until expiry so the buyer can retry (realistic retry semantics).\n   - success → insert attempt `succeeded`; `UPDATE orders SET status='paid', paid_at=now() WHERE id=$1 AND status='pending_payment'` (compare-and-set, must affect 1 row); `UPDATE offer_keys SET status='sold' WHERE order_item_id = ANY(items) AND status='reserved'` must affect exactly Σquantity rows else rollback 500; delete purchased offers from cart; commit.\n3. **Cancel** `POST /api/orders/{id}/cancel`: pending → `cancelled`, keys → available (`order_item_id` NULL) in one tx.\n4. **Expiry sweep** (single statement set in one tx): `UPDATE orders SET status='expired' WHERE status='pending_payment' AND expires_at<now() RETURNING id` → release their keys. Runs inline before create/pay (so stock recovers even when the free-tier instance was asleep) and on a 1-minute ticker.\n5. Network interruption: client retries with the same idempotency keys and gets the committed result; UI shows \"checking your order…\" and re-fetches `GET /api/orders/{id}`.\n\n**Payment UX:** `/checkout/:orderId/pay` titled \"Demo payment — no real money is charged\": order summary, timer to reservation expiry, buttons **Simulate successful payment** and **Simulate declined payment**; decline shows error with retry/cancel; success → `/orders/:id` with keys (copy button).\n\n**Auth & security:**\n- Passwords: bcrypt cost 12; length 8–72 bytes (bcrypt limit) enforced; email normalised; generic \"invalid email or password\"; unknown-email path still runs a bcrypt compare against a dummy hash (timing).\n- Sessions: 32-byte random token; DB stores SHA-256; new session on every login/registration (no fixation); absolute expiry 14 days, idle expiry 2 days (`last_seen_at` updated at most every 5 min); logout deletes the row and clears the cookie.\n- Cookie: prod `__Host-sid` (Secure, HttpOnly, Path=/, no Domain, SameSite=Lax); dev `sid` without Secure on http://localhost — chosen by config, never by request.\n- CSRF: Go stdlib `http.CrossOriginProtection` (Go ≥1.25; local 1.27) on all non-safe methods — rejects requests whose `Sec-Fetch-Site` is cross-site or whose `Origin` doesn't match, with `AddTrustedOrigin` for the exact Vercel production origin and `http://localhost:5173`; plus SameSite=Lax and JSON-only bodies (`Content-Type: application/json` required).
